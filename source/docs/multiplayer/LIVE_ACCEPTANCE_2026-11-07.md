# 2026-11-07 多人搜索深度实机对照

**保留生产多人默认三回合。** 本次六回合组在相同开战状态下完成了额外搜索，首个审核结果更晚，Solver Client 的峰值工作集和采样峰值私有内存更高。六回合仍未在该开战状态预测到胜利。连续出牌后两组均能恢复，实测刷新延迟和搜索期间的最大帧间隔接近。单人首个审核结果预测到第四回合获胜。

## 测试条件

- 游戏 0.107.1，同机 ENet，Steam 传输关闭。Host 为原版，Client 使用 `safe-execute-lab`，Mod 预热重启后的运行入档。两组 Client 启用同样的阶段统计，记录的并行上限均为 8，首个 Beam 宽度均为 60。
- 测试基于 `5d31fafc`。同一 DLL 通过隔离 Lab 入口切换，A 使用默认三回合，B 以三回合为起点、允许深入至六回合。入口仅在已授权 Lab 的多人本地核心策略下读取 `COMBATSOLVER_LIVE_ADAPTIVE_LIMIT=6`。两组共用原有预算。
- B 恢复 A 开战时的 Host 存档，场景为 `SHRINKER_BEETLE_WEAK`，双铁甲战士、进场时甲虫 88 HP。两组首回合公开根的手牌、抽牌堆、弃牌堆、能量、血量、敌人和 RNG 一致。前三回合前 17 个原生动作的牌名、出牌方和目标一致。第二、三回合可见同名打击的实例与弃牌顺序有差异。只比较到第三回合最后一次自动刷新，排除之后的手动请求和下一场战斗。

## 结果

| 指标 | 默认三回合 | 自适应上限六回合 |
|---|---:|---:|
| 首个请求到审核路线提交 | ≤2,781 ms | 3,473 ms |
| 首次搜索展开 / 模拟转移 | 445 / 1,063 | 1,634 / 4,049 |
| 首次搜索成员累计分配 | 46.2 MiB | 163.0 MiB |
| 首次预测 | 3 回合，敌人剩 61 HP | 6 回合，敌人剩 49 HP |
| Client 首次搜索最大主线程帧间隔 | 2,280.8 ms | 2,332.1 ms |
| 第 3 回合三次失效至有效搜索回调 | 414 / 365 / 377 ms | 348 / 365 / 380 ms |
| 上述三次刷新最大主线程帧间隔 | 26.1 ms | 26.2 ms |
| Client 峰值工作集 / 采样峰值私有内存 | 1,974.0 / 4,118.0 MiB | 2,241.9 / 4,444.7 MiB |
| Host 峰值工作集 / 采样峰值私有内存 | 1,448.2 / 2,333.1 MiB | 1,442.9 / 2,328.2 MiB |

两个 Client 首次入战的长帧都出现在冷启动搜索中，两组在首个搜索线程开始之前均已用时约 2 秒。第三回合三次有效刷新中，两组均未记录超过 50 ms 的帧。帧数据来自 Client 的 Godot 主线程，Host 本轮仅记录进程内存。内存窗口从首个请求到第三回合最后一次自动刷新，按约 200 ms 采样，工作集使用窗口内采样最大值，私有内存短于采样间隔的尖峰可能漏记。累计分配取搜索成员账本，与进程峰值分列。

第三回合 Host 三张打击都使甲虫血量从 33 依次降至 27、21、15。A 两次间隔约 0.79 s、2.46 s，B 约 0.57 s、0.67 s。A 的第一张发生在搜索运行中，旧请求以 `Superseded` / `Canceled` 收尾。B 的首张打击发生在当回合初次搜索完成后，随后两次记录 `stopped=observed_churn`。两组最后均发布了零追加战损的预测胜利路线。手动出牌节奏和相同卡牌实例的差异限制了取消成本与延迟的直接比较。

## 单人回归与证据

- 同一 Lab DLL 保持实验环境变量为 `6`，随后进入单人 `NIBBITS_WEAK`。实际可见游戏中的首个审核结果使用 `SinglePlayerFullRoute`，搜索 4 回合，预测第 4 回合胜利、敌方 0 HP、战损 3。该项核对了预测到终局及提交，战斗未按建议实际打完。
- 原始日志、进程内存 CSV、检查点和 Lab 构建改动保存在 `.local/churn-live-20261107/`。A 在进入下一场战斗时轮换了完整战斗日志。A 组保留进程时间线、世界状态、原生动作、内存采样和轮换前读到的请求数据，因此首个审核延迟以整个请求收尾时间作为上界，热态延迟用两组都有的回调时间计算。
- 此次对照覆盖了同机两端、连续敌方 HP 失效和单人预测。多次变更在同一个稳定窗口内合并、击杀旧目标、共享 RNG 与显式采用的专项验收仍按 [实机验收清单](LIVE_ACCEPTANCE.md) 单独记录。
